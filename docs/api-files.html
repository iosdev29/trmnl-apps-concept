Overview

An app never opens a network connection. It declares what it accepts in its manifest, and the firmware runs the upload: it joins Wi-Fi, shows a QR code in the TRMNL design, serves its phone page and stores the files in the app's own folder. The app then reads them with Files. Declaring the types is enough: the device's own page does the rest. An app may also ship its own page.

"uploads": { "accept": [".epub", ".txt"], "max_kb": 4096, "page": "upload.html" }   // "page" is optional
PartWhat it does
manifest uploadsthe file types the app takes, its total size cap and, optionally, its own page
the device's pagethe default: pairing code, "Add files to" the app, the types from the manifest, EPUB to text, compression, progress, the file list with Remove, the space left, Done
upload.htmloptional: the app's own page in the package, at most 64 KB. It is content only and talks to the same API (/api/info, /api/upload, /api/remove, /api/done)

Menu > Apps > the app > Upload filesstarts the same session without the app
onFilesChanged()when the upload ends, the firmware launches the app with this event, so it can open the new file

Whichever page the phone shows, the device enforces the session: the pairing code (and a limit on wrong codes), Wi-Fi only for the session with idle and total time caps, one upload at a time, the accepted types and file names, the app's max_kb and the shared quota, and only the app's own folder. A page is served with a Content-Security-Policy that lets it fetch, load and post only to the device.

A custom page is trusted at the level of the app's author. The policy blocks requests to other hosts but not a top-level navigation (location, window.open), so a hostile page could send away the files the user picks on the phone and the session's code. The device stays safe: no endpoint reads files back, and every limit is in the firmware. Reviewing app pages is part of app review.

In the Developer tab, turn on "Custom upload page" to edit upload.html (it starts as a copy of the device's page) and press "Upload page" to preview it as a phone against a mock of the device with the same rules; the app's requestUpload() opens the same preview, and the uploaded files reach the simulated app.

Formats

The firmware stores bytes as they arrive and checks only the extension against the manifest's accept list (and, for a compressed file, its container; see Compressed storage). What a format can do depends on what the app can show, and in v1 an app shows only TRMNL UI components: text, values, lists and the Reader. So:

Pagination

Only the device knows where a page ends (its fonts, its line breaking, its screen), so the firmware paginates a file for the reading layout: a Reader(_:_:) filling a Layout(_:) above a TitleBar(_:_:). It keeps a table of where each page starts in the app's folder and redoes it when the file, the font or the layout changes. A long book is laid out in steps of up to 0.8 s per call: paginate returns PAGINATING (-2) until it is done, so call it once per event (each press lays out more); the pages known so far can already be read. Then it returns the page count.

CallReturns
paginate(i)the page count when done, PAGINATING (-2) while not, -1 if the file cannot be paged
pageStart(i, n)the byte offset where page n (from 0) starts; n = the page count gives the end of the file; -1 if not known yet
pageOf(i, offset)the page that holds a byte offset: keep a reading position as an offset and it survives a new layout
readPage(i, n)exactly the text of page n, for Reader(text, page).label("n / count")

A message from the phone page

The app's phone page can leave the app one short message while the upload session runs: POST /api/message?m=<text>, 1 to 64 bytes of printable text, authorised by the session code like every call. The firmware stores it for the app and never interprets it; a new message replaces the old one. The app reads it once with Files.takeMessage() on its next event, for example in onLaunch, which every event starts with. Books uses goto:<page>:<file name> (page from 1) for its "Page [n] of N" control; /api/info reports pages for each file the app has paginated.

Compressed storage

The phone page stores text files (.txt, .md, .csv, .json, and converted EPUBs) compressed, and the app still reads plain text: size returns the uncompressed length and read takes offsets into the uncompressed data. The firmware decompresses only the 16 KB blocks a read needs, with the decompressor in the chip's ROM, and keeps the last block in memory, so reading page by page decompresses each block once. Text takes about 2.4 times less flash.

TRZ1 containerLittle-endian
0TRZ1 (magic)
4u16 version, 1
6u16 reserved, 0
8u32 block size, 16384
12u32 uncompressed length, up to 16 MB
16u32 block count, the length divided by 16384, rounded up
20u32 reserved, 0
24u32 index[count + 1]: offset of each block from the first one; the last entry is the total compressed size
thenthe blocks, each raw deflate (no zlib header) and independent; each at most 20 000 bytes

In the browser, CompressionStream("deflate-raw") produces the blocks. The file keeps its name and extension (Title.txt); the firmware recognises the container by its first bytes, and a plain file reads as before. A broken container reads as an error (-1), never as other data.

Reading

Files are addressed by index, 0 to count() - 1, in upload order. There are no paths: an app sees only its own folder. Read in chunks into a buffer; a wake has 512 KB of memory, far less than a book.

StorageValue
All apps together4 MB of flash, shared
Writes by the appnone, apart from remove

Reading does not wear the flash. A book is written once, at upload, and read on every page turn.
