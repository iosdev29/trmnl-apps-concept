Settings

Choices the user fills in, like a plugin's custom fields.

TRMNL UI 1.0 · App API v1 · TRMNL X · TRMNL OG

When the user should choose things (habit names, a city, a goal), declare a form in the manifest instead of hardcoding them. The user fills it in (in the Developer tab: Settings under the simulator; later on the phone page and trmnl.com) and the app reads it. The app never writes settings.

"settings": [{ "key": "habits", "type": "list", "label": "Habits", "max": 8,
  "fields": [{ "key": "name", "type": "text", "label": "Name", "max": 24 },
             { "key": "per_day", "type": "number", "label": "Per day", "min": 1, "max": 9, "default": 1 }] }]

Types: text, number, toggle, select (with options) and list (items of the other four). Give every field a label and a default, so the app works before the user saves anything. One app's values are at most 4 KB.

const n = Settings.count("habits");                    // items in a list
const name = Settings.getString("habits.0.name");
const perDay = Settings.getInt("habits.0.per_day");

onSettingsChanged(): void { this.render(this.body(), true); }  // App's default

Every field is always present and valid when the app reads it. Key the app's own data (KV) by something stable in the item, such as its name, not by its list index: the user may reorder or remove items.
